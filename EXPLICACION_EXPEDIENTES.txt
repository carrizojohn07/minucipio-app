1. ¿QUE ES EL MODULO DE EXPEDIENTES Y CUAL ES SU OBJETIVO?
--------------------------------------------------------------------------------

El modulo de Expedientes (/expedientes y /expedientes/[id]) digitaliza la mesa de
entradas, el circuito administrativo municipal y el seguimiento ciudadano de
tramites publicos e internos (tales como habilitaciones comerciales, obras
particulares, reclamos administrativos, auditorias, licitaciones, etc.).

A diferencia de un reclamo vecinal simple, un expediente administrativo:
  - Posee un numero oficial correlativo unico (ej: EXP-2026-000101).
  - Tiene una caratula (titulo formal) y un extracto (resumen del objeto).
  - Esta radicado en un Area Municipal responsable en cada momento.
  - Posee un historial cronologico de "Pases" o "Movimientos" (actuaciones,
    dictamenes tecnicos o legales, observaciones e intimaciones).
  - Puede tener un Vecino Titular asignado o ser una actuacion interna de oficio.
  - Puede ser marcado como publico o reservado/confidencial.


--------------------------------------------------------------------------------
2. NIVELES DE ACCESO Y REGLAS DE PRIVACIDAD POR ROL
--------------------------------------------------------------------------------

El sistema implementa una matriz de permisos estricta tanto en la interfaz de
usuario como a nivel backend (Base de Datos y Server Actions):

A) VISITANTE ANONIMO / NO REGISTRADO:
   - Solo tiene acceso al Buscador Publico por numero de expediente.
   - Si el expediente es PUBLICO: Unicamente puede ver el numero de expediente,
     el estado actual y el area municipal donde se encuentra alojado.
   - NO puede ver caratula sensible, extracto, dictamenes tecnicos ni historial
     de pases (por proteccion de datos personales y secreto administrativo).
   - Si el expediente fue marcado como CONFIDENCIAL / RESERVADO (esPrivado = true):
     El sistema le bloquea la visualizacion con un aviso de que el tramite esta
     reservado para autoridades o su titular autenticado.

B) VECINO AUTENTICADO (ROL "VECINO"):
   - Si busca un expediente del cual NO es titular: Recibe la vista reducida de
     consulta publica comun.
   - Si es el TITULAR del expediente (usuario.vecinoId == expediente.vecinoId):
     El backend le desbloquea el acceso completo:
       * Caratula y extracto completo.
       * Historial integro de pases y dictamenes tecnicos.
       * Formulario para "Aportar Documentacion o Responder Observaciones": si el
         expediente fue observado por un inspector, el titular puede enviar su
         descargo directamente, reactivando el tramite a estado EN_TRAMITE.
   - Seccion "Mis Expedientes": Ve una grilla con todos los tramites a su nombre.
   - Formulario "Iniciar Nuevo Tramite": Puede autogenerar un expediente oficial
     directamente desde su portal digital.

C) PERSONAL MUNICIPAL (ROLES "ADMIN" Y "EMPLEADO"):
   - Acceso irrestricto a todos los expedientes del municipio, incluidos los
     reservados o confidenciales.
   - Dashboard de metricas: Total, Iniciados, En Tramite, Observados y Cerrados.
   - Bandeja general con filtros rapidos por estado (INICIADO, EN_TRAMITE, etc.).
   - Apertura de nuevos expedientes oficiales (con autogeneracion de numero o
     ingreso de numero manual, asignacion de vecino titular y tilde de confidencial).
   - Panel Operativo de Dictamenes: Puede asentar nuevos pases, cambiar de estado,
     derivar el expediente a otra area municipal, escribir resoluciones y marcar
     pases especificos como reservados.
   - Rol "ADMIN" exclusivo: Puede eliminar expedientes de forma definitiva.

3. ¿COMO SE RELACIONA CON EL BACKEND?
--------------------------------------------------------------------------------

El modulo opera 100% sobre el stack de backend de Next.js (App Router) y Prisma:

3.1. MODELO DE DATOS EN POSTGRESQL (prisma/schema.prisma)
----------------------------------------------------------
Se agregaron/actualizaron dos modelos principales y un enumerador:

a) enum EstadoExpediente:
   - INICIADO: Ingreso en mesa de entradas o apertura digital.
   - EN_TRAMITE: En evaluacion tecnica o circulando por areas.
   - OBSERVADO: Paralizado a la espera de documentacion o subsanacion del titular.
   - CERRADO: Finalizado con resolucion definitiva (favorable o rechazo).

b) model Expediente:
   - id: String (cuid autogenerado).
   - numero: String @unique (clave publica, ej: EXP-2026-000101).
   - caratula: String (titulo publico/institucional).
   - extracto: String (resumen formal del objeto del expediente).
   - tipo: String (ej: "Habilitacion comercial", "Obras particulares", etc.).
   - estado: EstadoExpediente (default: INICIADO).
   - esPrivado: Boolean (default: false, controla si es confidencial).
   - fechaInicio: DateTime (default: now()).
   - fechaCierre: DateTime? (null mientras siga en curso).
   - vecinoId: String? (relacion N:1 opcional con modelo Vecino).
   - areaId: String (relacion N:1 obligatoria con modelo Area).
   - movimientos: MovimientoExpediente[] (relacion 1:N con sus pases).

c) model MovimientoExpediente:
   - id: String (cuid).
   - expedienteId: String (con onDelete: Cascade para borrado limpio).
   - estadoNuevo: EstadoExpediente (estado al que pasa el expediente en este pase).
   - comentario: String? (dictamen tecnico, motivo del pase o resolucion).
   - esConfidencial: Boolean (default: false).
   - fecha: DateTime (default: now()).

3.2. MANEJO DE SESION Y SEGURIDAD EN EL BACKEND
------------------------------------------------
- Las sesiones residen en cookies HTTP-only bajo la clave 'sesion_usuario_id'.
- Toda operacion del backend lee la cookie de forma segura en el servidor,
  recuperando el registro del usuario con sus relaciones (vecino y empleado).
- Las Server Actions nunca confian en datos ocultos del cliente: la identidad
  del autor de una accion se extrae estrictamente de la sesion del servidor.

3.3. CLIENTE DE BASE DE DATOS SINGLETON (src/lib/prisma.ts)
------------------------------------------------------------
- Las consultas y mutaciones se hacen a traves de la instancia global de Prisma,
  evitando la saturacion del pool de conexiones de PostgreSQL en desarrollo y
  produccion.

3.4. RENDERIZADO EN EL SERVIDOR (SERVER COMPONENTS)
----------------------------------------------------
- src/app/expedientes/page.tsx y src/app/expedientes/[id]/page.tsx son Server
  Components ("force-dynamic").
- Consultan la base de datos directamente con Promise.all() antes de generar el
  HTML, garantizando que el usuario solo reciba los datos que su perfil esta
  autorizado a ver.

4. DETALLE DE LAS FUNCIONES AGREGADAS
--------------------------------------------------------------------------------

A continuacion se desglosan las funciones creadas para este modulo:

================================================================================
A) SERVER ACTIONS Y LOGICA DEL SERVIDOR (src/app/expedientes/actions.ts)
================================================================================

1. getUsuarioSesion() [Privada / Helper]:
   - Tipo: Helper asincrono de autenticacion.
   - Funcion: Lee la cookie 'sesion_usuario_id', busca el usuario en PostgreSQL
     e incluye sus perfiles de Vecino o Empleado. Si no hay cookie valida, retorna null.

2. generarProximoNumeroExpediente() [Privada / Helper]:
   - Tipo: Generador de numeracion oficial correlativa.
   - Funcion: Obtiene el año actual (YYYY), cuenta los expedientes existentes y
     busca el proximo valor disponible con formato EXP-YYYY-XXXXXX (ej: EXP-2026-000105).
   - Garantiza que nunca se produzca una colision por clave duplicada en la base de datos.

3. crearExpediente(formData: FormData) [Exportada]:
   - Tipo: Server Action (Mutacion de formulario).
   - Que hace:
     * Verifica que el usuario haya iniciado sesion.
     * Si es Personal Municipal (ADMIN/EMPLEADO): Permite asignar un vecino titular
       o dejarlo de oficio (sin titular), ingresar un numero personalizado o autogenerarlo,
       y definir si es un expediente privado (esPrivado = true).
     * Si es Vecino: Fuerza la autogeneracion del numero oficial, se asigna a si
       mismo como titular y crea el tramite en modo publico.
     * Crea atomicamente el registro en la tabla Expediente y el primer
       MovimientoExpediente con la nota de apertura en mesa de entradas.
     * Revalida la ruta /expedientes con revalidatePath() y redirige al expediente creado.

4. agregarMovimiento(formData: FormData) [Exportada]:
   - Tipo: Server Action (Gestion de dictamenes y pases).
   - Que hace:
     * Proteccion: Solo admite usuarios con rol "ADMIN" o "EMPLEADO".
     * Lee el id del expediente, el nuevo estado, la observacion/dictamen y el area de destino.
     * Actualiza el modelo Expediente con el nuevo estado y reasigna el areaId si
       hubo derivacion a otra dependencia.
     * Si el nuevo estado es CERRADO, estampa automaticamente la fechaCierre actual.
     * Inserta un nuevo registro en MovimientoExpediente con el dictamen.
     * Revalida en cache /expedientes y las URLs individuales.

5. agregarObservacionVecino(formData: FormData) [Exportada]:
   - Tipo: Server Action (Respuesta ciudadana a observaciones).
   - Que hace:
     * Proteccion: Requiere usuario autenticado con rol "VECINO".
     * Verifica que el usuario sea el dueño legitimo (vecinoId) del expediente.
     * Si el expediente ya estaba CERRADO, rechaza la peticion.
     * Si el expediente estaba en estado OBSERVADO, lo transiciona automaticamente
       a EN_TRAMITE para reactivar su curso en la oficina correspondiente.
     * Guarda el descargo del vecino en la tabla MovimientoExpediente con el prefijo
       "Presentacion del titular: ...".

6. eliminarExpediente(formData: FormData) [Exportada]:
   - Tipo: Server Action (Administracion y mantenimiento).
   - Que hace:
     * Proteccion estricta: Solo autoriza usuarios con rol "ADMIN".
     * Elimina el expediente de la base de datos (y gracias a onDelete: Cascade
       en Prisma, borra en cascada todos los movimientos asociados).

================================================================================
B) COMPONENTE DE PRESENTACION (src/app/expedientes/expediente-view.tsx)
================================================================================

7. getEstadoExpedienteBadge(estado: EstadoExpediente) [Exportada]:
   - Tipo: Componente/Helper de renderizado de insignias.
   - Funcion: Retorna badges estilizados con Tailwind segun el estado:
     * INICIADO -> Celeste (sky).
     * EN_TRAMITE -> Azul (blue).
     * OBSERVADO -> Amarillo/Ambar (amber).
     * CERRADO -> Verde (emerald).

8. ExpedienteView(props) [Exportada]:
   - Tipo: Componente de visualizacion reactivo a los permisos.
   - Funcion: Contiene la logica de renderizado condicional en tres ramas:
     * Rama 1: Si es privado y el usuario no es titular ni personal municipal,
       muestra el bloqueo por confidencialidad.
     * Rama 2: Si el usuario es anonimo o vecino no titular, renderiza la tarjeta
       publica simplificada (solo numero, estado actual y area de radicacion).
     * Rama 3: Si es titular o personal municipal, despliega la ficha completa,
       caratula, extracto, metadatos y el timeline vertical interactivo de todos
       los pases y dictamenes. Ademas habilita los formularios de dictamenes
       o respuestas segun el rol del usuario.

================================================================================
C) VISTAS Y RUTAS (src/app/expedientes/page.tsx y [id]/page.tsx)
================================================================================

9. ExpedientesPage({ searchParams }) [Default Export]:
   - Tipo: Server Component de la ruta /expedientes.
   - Que hace:
     * Lee la sesion activa del usuario y las areas registradas.
     * Ejecuta la busqueda si el usuario ingreso un numero de expediente.
     * Si el usuario es VECINO: Consulta en PostgreSQL sus propios tramites
       ("Mis Expedientes") y renderiza el formulario de inicio digital.
     * Si el usuario es ADMIN/EMPLEADO: Calcula metricas en tiempo real, aplica
       filtros por estado/area, lista todos los expedientes del municipio y
       despliega el formulario de apertura oficial.
     * Si es ANONIMO: Muestra el buscador rapido, chips de prueba y banners informativos.

10. ExpedienteDetailPage({ params }) [Default Export]:
    - Tipo: Server Component de la ruta /expedientes/[id].
    - Que hace:
      * Permite acceder de forma directa mediante enlace permanente (ej: /expedientes/EXP-2026-000101
        o mediante el ID interno de cuid).
      * Valida la existencia con Prisma; si no existe ejecuta notFound() (404).
      * Reutiliza ExpedienteView aplicando exactamente las mismas reglas de seguridad.


--------------------------------------------------------------------------------
5. CICLO DE VIDA Y TRANSICIONES DE ESTADO DEL EXPEDIENTE
--------------------------------------------------------------------------------

Flujo estandar de un expediente en el sistema:

  [ MESA DE ENTRADAS ]
           │
           ▼
     ( INICIADO ) ────► Se crea el expediente y el 1° movimiento formal.
           │
           ▼
    ( EN_TRAMITE ) ◄─── (El area competente evalua planos/documentos)
        │      ▲
        │      │ (Vecino subsana con "Aportar Documentacion")
        ▼      │
    ( OBSERVADO ) ────► Se solicita seguro, plano o correccion al titular.
        │
        ▼ (Dictamen definitivo o aprobacion)
     ( CERRADO )  ────► Se asienta fechaCierre. Fin de las actuaciones.
